산출물 하나는 3× 평면 중 정확히 하나에 속한다. 평면이 저장 위치를 정하고, 그 기계가 죽어도 남는지를 정한다. 베이스 평면에서 규범은 spec/campaign/ 의 5× 엔티티 로 된 모듈 하나고, 독자를 위해 그린 뷰는 docs/ 의 HTML이다. 다섯 엔티티는 층이고, 각각 아래를 open 한다. github, directory, synchronization, session, orchestration 순으로 쌓이므로 맨 위가 곧 합쳐진 모델이다. 엔티티 하나는 3× 파일 이다. system.als 가 그것을 구현하는 스크립트와 스킬의 설계, scenarios.als 가 그 시험의 설계, checks.als 가 성립해야 하는 성질이다. 명령은 뒤의 둘에만 있으므로 system.als 를 실행하면 아무 명령도 돌지 않는다. 무엇을 검사하는지는 그 파일의 주석에 적는다. 모델 옆에 둔 산문은 모델에서 멀어지고, 모델 안에 쓴 주석은 멀어지지 않는다. 그래서 spec/ 아래에 마크다운은 없다. 예외는 모듈 옆의 diagram.html 하나다. AGENTS.md, spec/campaign/github/system.als @ 03643fb

캠페인 디렉터리는 자기 평면이 없다. 이미 다른 곳에서 버전 관리되는 것들을 모아 둔 임시 조립물이다. 그래서 .gitignore 가 무시한다. 무시 규칙은 허용 목록이라서, 추적되는 디렉터리는 !/docs/ 처럼 자기 줄을 가진다. .gitignore @ 24cb850

⚠️

캠페인 디렉터리는 지워져도 된다. 오직 거기에만 있는 것은 남지 않으므로, 남아야 하는 것은 GitHub 이슈나 저장소 원격에 먼저 올린다.

기계로 옮기면 실패가 조용해진다. 세션 id가 바뀌고, 이름이 바뀌고, 맥락이 압축되고, 기대한 파일이 애초에 없었던 경우가 모두 검사에는 없음 으로 똑같이 도착한다. 그래서 검사는 보았더니 없었다 와 볼 수 없었다 를 갈라야 하고, 무엇을 어디에서 읽었으며 어느 갈래를 탔는지 찍어야 한다. 판정 단어 하나만 내놓는 검사는, 아무것도 강제하지 않으면서 몇 달 동안 믿긴다.

캠페인 개시 순서

디렉터리 이름은 지역 편의고, ID가 정체성이다. 캠페인을 넘겨준 기계에 날짜만 다른 디렉터리가 남아 있어도 아무것도 깨지지 않는다. 어느 디렉터리도 권위를 가지지 않기 때문이다. spec/campaign/directory/ @ 03643fb

앵커 이슈 본문은 비교한 뒤에 쓴다. gh issue edit 직전에 본문을 다시 읽고, README.md 를 뽑아낸 뒤로 본문이 움직였으면 쓰지 않는다. 이 비교가 상시 안전장치다. 캠페인 하나가 기계 하나에 묶여도 본문은 직렬화되지 않는다. 한 기계가 여러 캠페인을 동시에 들고, 그 기계의 두 세션은 모두 이 캠페인의 세션이라 손실이 그대로 돌아온다. 비교만으로 막힌다. 본문이 움직인 이유는 셋이다. 같은 기계의 다른 세션이 썼거나 — 하위 과제를 캠페인 사이로 옮기면 앵커를 둘 쓰게 되고 그중 하나는 쓴 쪽의 캠페인이 아니다 — 사람이 GitHub에서 헌장을 고쳤거나, 앵커가 묶이지 않은 기계의 세션이 썼거나다. 첫째는 동료 세션에게 물으면 갈린다. 뒤의 둘은 이 기계에서 갈리지 않는다. 계정 하나가 사람의 편집과 세션의 편집에 똑같이 서명하기 때문이다. 그래서 거절은 셋을 다 부르고, 갈리지 않는 둘을 갈리지 않는다고 말한다. 본문을 쓰는 것은 역할이 아니다. 두 순간에, 그 일을 하는 쪽이, 이 비교를 거쳐 쓴다. spec/campaign/session/ @ 03643fb

하위 과제 발행과 브랜치 청구

하위 과제 하나는 GitHub 이슈 하나다. 이슈는 코드가 어느 저장소에 있든 베이스 트래커에 산다. 멤버 저장소는 브랜치와 풀 리퀘스트만 받으므로 그 저장소의 이슈 관례를 건드리지 않고, 이 계정 소유가 아닌 저장소도 두 저장소를 한꺼번에 움직이는 과제도 예외가 되지 않는다. --parent 가 이슈를 하나의 색인으로 묶고, 풀 리퀘스트 본문의 Closes kalaluthien/campaign-base#<issue> 가 이슈를 저장소 너머에서 닫는다. 짧은 #<issue> 는 멤버 저장소의 같은 번호 이슈를 닫는다.

색인은 한 번의 호출로 되읽는다. gh api --paginate repos/kalaluthien/campaign-base/issues/6/sub_issues 는 캠페인 #6 의 구성원을 정확히 돌려준다. 저장소가 비공개여도 공개 부모 아래에서 올바르게 나열된다. 이 끝점은 서른 개에서 쪽을 나누고, 잘린 색인은 온전한 색인과 똑같이 읽히므로 --paginate 는 선택 사항이 아니다. 본문에는 Campaign: 줄이 없다. 아무도 읽지 않는 산문이었고, 색인은 --parent 하나뿐이므로 #217에서 지웠다. AGENTS.md @ 24cb850, kalaluthien/campaign-base#217

4× 색인 방식 중 서브이슈 링크만 도달 가능한 모든 상태에서 색인과 실제 구성원이 같았다
  • 역참조 줄 — 추가만 된다. 캠페인에서 빠져나간 하위 과제가 영원히 색인에 남는다.
  • 앵커 본문 체크리스트 — 다른 객체에 하는 두 번째 쓰기다. 건너뛰면 이슈가 아무 반박 없이 사라진다.
  • 저장소마다 다는 campaign-<N> 라벨 — 맞기는 하다. 저장소마다 라벨을 만들어야 하고, 떼어낸 뒤에도 흔적으로 남는다.
  • 서브이슈 링크 — 색인이 곧 구성원이다. 하나의 명령이 만들고, 하나의 호출이 읽는다.

spec/campaign/github/ @ 03643fb

브랜치는 campaign-<N>/<issue>-<topic> 이고, 하위 과제의 작업 공간이자 청구다. 이슈 번호는 이슈가 만들어질 때 발행되므로 청구는 발행을 뒤따르고, 작업자를 붙이기 전에 원격에 만든다. create-ref는 이미 있는 ref를 서버에서 거절하므로 청구는 원자적이다. 같은 SHA로 두 번째로 만들면 422 와 Reference already exists 가 돌아온다. 거절은 다른 작업자가 그 하위 과제를 잡았다는 뜻이고, 밀고 지나가지 않는다. 첫 커밋 전에 작업자가 죽어도 청구는 모든 기계에서 보인다. AGENTS.md, spec/campaign/github/ @ 03643fb

하위 과제의 세 실행 방식

실행 방식도는 곳고르는 조건
세션의 손베이스 루트한눈에 들어오는 작은 편집 하나
인프로세스 서브에이전트그 저장소의 git 워크트리독립된 하위 과제 여럿을 한꺼번에
herdr 저장소 에이전트<campaign>/repos/<repo>/ 클론저장소의 도구가 필요하거나 여러 턴이 걸린다

하위 과제 하나는 3× 실행 방식 중 하나로 돌고, 방식은 일을 시작하기 전에 정한다. 첫 질문은 그 저장소의 맥락을 불러와야 잘 할 수 있는가다. 재는 비용은 턴이다. 생성 한 번과 인수인계 한 번이 드는 위임은 몇 턴을 넘는 일에서 더 싸다. 병렬성도 그 자체로 넘기는 이유가 된다. 각각 작아도 여럿인 하위 과제를 세션이 직접 하면 차례로 하게 되기 때문이다. spec/campaign/orchestration/ @ 03643fb

실행 방식은 저장소가 먼저 정하고, 비용은 그다음이다. 저장소를 바꾸는 작업자는 그 저장소의 체크아웃에서 시작된 프로세스에서 돈다. 멤버 저장소면 <campaign>/repos/<repo>/ 의 herdr 위임이고, 베이스 자신이면 이 캠페인의 세션이거나 워크트리 위의 서브에이전트다. 둘 다 이미 베이스의 스킬을 가지고 있기 때문이다. 저장소를 읽기만 하거나 <campaign>/ 아래에 쓰는 일은 어느 방식으로도 된다. 근거는 하네스 사실 하나다. 서브에이전트와 대화형 세션은 자기가 시작된 곳의 스킬만 불러오고, 다른 저장소가 어떻게 체크아웃되어 있든 그쪽 스킬은 불러오지 않는다. disable-model-invocation: true 스킬은 어느 방식에서도 에이전트가 쓸 수 없으므로 브리프에 풀어 적어야 한다. AGENTS.md @ c87b208, spec/campaign/orchestration/ @ 03643fb

🔔

네 번째 작업자는 스스로 온다. 베이스 루트에서 열려 하위 과제 하나를 맡은 세션이 곧 작업자 세션 이다. 브랜치를 청구하고 그 브랜치를 체크아웃한 뒤로는 다른 작업자와 똑같다. STATUS 에 답하고, REPORT 와 BLOCKED 를 보내고, STAND DOWN 에 멈춘다. 앵커 본문은 두 순간에만 쓰이고 하위 과제는 그 두 순간이 아니므로 손대지 않는다. 병합은 역할이 아니라 조건이 정한다. 5번의 세 조건을 채우면 자기 풀 리퀘스트도 자기가 병합한다. 위 규칙 때문에 작업자 세션이 직접 잡을 수 있는 것은 베이스 하위 과제와 캠페인 디렉터리 작업뿐이고, 멤버 저장소 하위 과제에서는 위임자를 띄우는 쪽이 된다. 그때 ref는 띄우는 쪽이 미리 자르고, 청구를 쥔 것은 그 ref를 체크아웃한 위임자다.

워크트리는 클론이 틀린 물건일 때 쓴다. 대상 저장소가 베이스 자신이면 클론해 넣을 곳이 없다. 캠페인 디렉터리가 선택 사항이라 없을 수 있기 때문이다. 워크트리는 잘라낸 체크아웃과 .git 하나를 공유하므로 잘라내는 순간에 뒤처질 수 없다. 서브에이전트는 프로세스 경계를 넘지 않으므로 브리프를 따로 건네줄 일도, herdr 생존 확인도 필요 없다. spec/campaign/synchronization/, spec/campaign/orchestration/ @ 03643fb

멤버 저장소가 없는 캠페인은 ## Repos 에 - none 하나만 적고, 클론해 넣을 저장소가 없으므로 앞의 두 방식만 가지며, 하위 과제는 ref를 자를 유일한 저장소인 베이스의 campaign-<N>/<issue>-<topic> ref로 청구한다. AGENTS.md, spec/campaign/session/ @ 03643fb (PR #46)

브리프는 하위 과제 자체다

herdr 위임의 브리프는 하위 과제 이슈의 본문이다. 실행 프롬프트는 그 번호를 가리키는 짧은 문장 하나다. 쓸 것이 없으니 낡을 것도 없고, 브리프가 기계보다 오래 산다.

브리프를 실행 줄에 적는다

터미널은 1024바이트를 넘는 줄을 조용히 버린다. 아무것도 실행되지 않고, 실패는 느린 에이전트처럼 보인다.

herdr 위임은 <campaign>/repos/<repo>/ 에서 실행하고, 캠페인의 원칙은 그 클론 안의 CLAUDE.local.md 로 건네주며 그 경로를 클론의 .git/info/exclude 에 적어 둔다. 위임자 자기 자리에 있는 파일이라 도착했는지 증명할 것이 없다. 이름은 --name 으로 campaign-<campaign issue>-<role>-<n> 을 준다. 이 기계의 모든 세션에 걸리는 하나의 규칙이고, 위임자도 작업자라 자기 역할 단어를 따로 갖지 않는다. 하위 과제는 일부러 이름에 넣지 않는다. 한 세션이 하위 과제를 여러 개 이어서 하므로, 하위 과제를 담은 이름은 넘길 때마다 거짓이 된다. --name 은 하네스 이름만 바꾸므로 herdr 창 이름도 같이 줘야 하고, scripts/campaign-name-session.py 이 그 둘을 한 번에 세우는 이 규칙의 유일한 소비자다. 상위 지시 파일은 그 디렉터리에 hasClaudeMdExternalIncludesApproved 가 켜져야 읽힌다. 기본값은 거짓이고, 대화형 대화 상자로 묻는다. 방금 가져온 저장소는 정확히 그 값이 꺼져 있는 상태다. 자기 작업 디렉터리의 CLAUDE.local.md 는 상위 가져오기가 아니므로 그 승인에 기대지 않는다. AGENTS.md @ 24cb850

갓 시작한 위임은 세 곳에서 조용히 멈추고, 밖에서는 셋 다 생각 중인 에이전트로 보인다
  • 폴더 신뢰 질문 — 아무것도 읽지 않은 채 대화 상자에 앉는다.
  • 상위 CLAUDE.md 외부 임포트 질문 — 같은 모습이다. 거절되면 캠페인 원칙이 말없이 빠진다.
  • 첫 셸 명령 권한 질문 — --permission-mode acceptEdits 는 편집만 덮으므로 첫 ls 에서 멈춘다.

베이스는 자기 캠페인의 멤버가 될 수 있다. 그때 저장소 하나가 2× 체크아웃 을 가지므로, 클론 안에서 고친 스킬은 병합하고 당겨오기 전까지 실행 중인 캠페인을 바꾸지 않는다.

캠페인과 에이전트 사이의 네 메시지

세 시스템이 각각 다른 질문에 답한다. 일이 끝났는가는 GitHub이 답하고, 프로세스가 살아 있는가는 herdr이 답한다. 무엇을 하고 있으며 무엇을 기다리는가는 에이전트 자신만 안다. 이 프로토콜은 세 번째만 나른다. GitHub 사실이나 herdr 사실을 되풀이하는 메시지는 두 번째 사본을 만들고, 낡는 쪽은 언제나 사본이다. spec/campaign/orchestration/ @ 03643fb

완료와 생존을 서로의 답으로 쓰지 않는다. 밀어 놓고 죽은 위임자는 성공한 것이다. 살아서 말이 많은 위임자는 아무것도 하지 않았을 수 있다. 생존은 herdr agent list 가, 청구의 존재는 원격의 campaign-<N>/ ref들이, 그 청구를 누가 붙잡고 있는지는 git worktree list 가 답한다. 셋 중 하나라도 읽히지 않으면 아래의 어떤 숫자도 믿을 수 없다. ListAgents 이름을 브랜치와 맞춰 보는 것으로는 안 된다. 이름과 브랜치는 일부러 다른 두 문자열이고, 이름은 어느 캠페인인지만 말할 뿐 어느 하위 과제인지는 말하지 않으므로, 문자열로 맞춰 보면 우연히 맞는 것만 걸리고 나머지를 통째로 놓친다. agent_status 하나로는 읽지 않는다. 그 값은 화면을 보고하며 턴 중간의 멈춤을 idle 이라고 부른다. 대신 blocked 는 즉시 움직일 값이다. 다만 사용량 한도 메뉴도 창을 똑같이 막으면서 idle 로 보고하므로, 조용한 시간을 재는 타이머를 함께 둔다.

캠페인 종료 조건

끝난 에이전트는 캠페인이 닫힐 때가 아니라 캠페인이 도는 동안 물러난다. 오래 가는 캠페인은 하위 과제를 계속 끝내고, 창은 아무도 쓸지 않으면 쌓인다. 청구를 쥔 작업자는 리뷰 결과를 기다린다. 병합하는 쪽이 그쪽이기 때문이다. 새 세션으로 넘기는 것은 긴 고침 회차이고, 풀 리퀘스트와 리뷰로 브리핑한다. spec/campaign/orchestration/ @ 03643fb

캠페인이 가지지 않는 것

  • 티켓 시스템이 없다. 캠페인은 사람이 시작하고, 하위 과제는 GitHub 이슈가 나른다.
  • 캠페인 차원의 git이 없다. 캠페인 디렉터리는 커밋되지 않는다.
  • 기계 위에 상태가 없다. 캠페인 디렉터리는 repos/ 와 본문 사본을 담은 캐시일 뿐이고, GitHub 사실의 두 번째 사본을 만들지 않는다. 청구도 결속도 브리프도 GitHub에 있다.
  • 하트비트가 없다. 생존은 이미 herdr 사실이고, 하트비트는 에이전트가 바쁘기만 해도 멈춘다.
  • 과제 배정 메시지가 없다. 브리프는 하위 과제 이슈다.
  • 자기 종료가 없다. 위임자의 작업을 검증할 수 있는 것은 그 위임자가 아닌 무언가뿐이다.
  • 멤버 저장소들을 가로지르는 하나의 git 명령이 없다. 멤버 저장소의 파일은 베이스에 커밋하지 않는다.
  • 기계 사이의 합의가 없다. 대신 캠페인 하나가 기계 하나에 묶이고, 그 자리는 앵커의 bound:<machine> 라벨 하나가 정한다. 라벨은 이름으로 정확히 읽히고 이력이 없으므로 최신을 고를 일이 없다. 두 개가 붙은 상태는 고르는 대신 거절한다. 옮기는 방법은 사람이 말하고 묶일 기계가 라벨을 다시 다는 것뿐이다.

리뷰를 지켜보는 것도 없다. 풀 리퀘스트가 열린 시점에 에이전트가 물러나므로, 보드가 생기기 전까지는 사람이 알아채는 쪽이다. spec/campaign/github/ @ 03643fb
