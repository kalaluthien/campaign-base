A sub-issue's lifecycle

A sub-issue is filed, claimed, committed, reviewed, merged, reached and closed, and at each step a named reader on GitHub or on disk, never a terminal screen, says whether the step happened.

Map

  1. File: how does a sub-issue come to exist?
  2. Claim: how does one session come to own it?
  3. First commit: when does the work become visible?
  4. Review: who judges the work, and at which revision?
  5. Merge: who may land it?
  6. Reach: when is a merge finished on this machine?
  7. Close: when is the sub-issue settled?

File: how does a sub-issue come to exist?

Next step
create it on the base's tracker as a sub-issue of the campaign issue, gh issue create --parent, its body from the sub-issue template and one kind: label
Who
any session on any machine, one outside the campaign included; the planner, when the work is decomposed
Settled by
scripts/campaign-tracker.py index <N> reads the link back; campaign-tracker.py check <issue> reads the shape

The sub-issue link is the whole index: nothing else lists a campaign's sub-issues. Filing is a record, not a claim, so it asks for no binding. A sub-issue labelled backlog waits for the owner to take the label off.

Evidence: spec/campaign/github/system.als § addMember
Deliberately no session, machine or binding precondition: filing a sub-issue is a record, not a claim, so any session on any machine may do it (AGENTS.md § The binding).

  • AGENTS.md § Sub-issues
  • scripts/campaign-tracker.py, its docstring

Claim: how does one session come to own it?

Next step
scripts/campaign-claim.py take <N> <issue> <topic> cuts the branch <slug>/<issue>-<topic> from the remote, on the repository the work lands in, or on the base when it lands nowhere
Who
the worker; the planner, before it launches a delegate onto the branch
Settled by
GitHub's create-ref, which refuses a ref that exists, so the claim is atomic across machines; campaign-claim.py live <N> says which claims are checked out on this machine

The branch is the whole claim and its workspace. Work that lands no commit is claimed all the same, and a sub-issue has one claim whatever the topic.

Evidence: spec/campaign/github/system.als § claim
the ref that carries a claim is named `<slug>/<issue>-<topic>`, so create-ref's server-side refusal serialises ref NAMES and admits two topics on one sub-issue. [...] What closes it is in the script: `take` reads the campaign's refs again AFTER its own create, and where two name one sub-issue, EVERY taker that sees a rival deletes what it just cut.
  • spec/campaign/github/system.als, claim
  • AGENTS.md § ID, slug, directory, branch, Branch
  • scripts/campaign-claim.py, its docstring

First commit: when does the work become visible?

Next step
commit on the claim branch in the checkout it names, then open the pull request at once, its body closing the sub-issue by full name, Closes kalaluthien/campaign-base#<issue>
Who
the worker
Settled by
the pre-commit hook's scripts/check-commit-claim.py, which refuses a commit on campaign work whose branch is not a claim; the post-commit hook's scripts/push-campaign-branch.sh, which pushes and says what happened

The push has already published the branch, so a late pull request only hides published work. The open pull request is where the review writes its findings, and it outlives the session that opened it.

Evidence: spec/campaign/orchestration/system.als § push
it clears `Reviewed`, because A REVIEW IS OF A PULL REQUEST AT A REVISION.
  • spec/campaign/orchestration/system.als, push
  • AGENTS.md § Execution mode
  • scripts/check-commit-claim.py, its docstring

Review: who judges the work, and at which revision?

Next step
a REVIEW comment on the pull request naming the head sha, written by an in-process subagent
Who
written by an agent that did not write the commits; launched by whoever wants the merge, the author included
Settled by
scripts/check-merge-review.py, which answers reviewed, unreviewed or unknown for a sha; scripts/rerun-check.py re-runs the pull request's check once a REVIEW names its head

Every push retires the review, so the author posts a REPORT pinning the new sha and asks for the next one. A silent wait looks the same as work.

Evidence: spec/campaign/orchestration/system.als § review
No guard on who commissions it -- the property needs independence of JUDGEMENT, not of TASKING, and a one-session campaign has nobody else to launch it. The named limit: the launcher writes the reviewer's brief.
  • spec/campaign/orchestration/system.als, review
  • assuming-role/references/reviewing.md § The call
  • scripts/check-merge-review.py, its docstring

Merge: who may land it?

Next step
merge the pull request once a review was read at the sha being merged, written by an agent that did not write the commits, and the branch contains the current main; when main has moved, merge it into the topic branch first, which is a push and so needs a fresh review
Who
anyone who satisfies all of those, the author included; no role is named
Settled by
GitHub's required check job, which holds the review-at-sha and contains-main conditions; the not-the-author condition has no automatic reader and rests on the reviewer saying so honestly

A branch that was never a pull request head has no check, so fast-forwarding main onto it is refused; landing goes through the pull request.

Evidence: spec/campaign/orchestration/system.als § Plane
`MergePullRequest` is on neither plane deliberately: AGENTS.md's three merge conditions hold it and none of them names a role, so putting it on the code plane would make a planner unable to land a reviewed pull request and putting it on the campaign plane would let one land any.
  • spec/campaign/orchestration/system.als, the Plane comment
  • AGENTS.md § Merge conditions

Reach: when is a merge finished on this machine?

Next step
scripts/campaign-installed.py reach <body> <owner/repo> <sha> for the repository the merge landed in: it fast-forwards the install and runs its apply, and the REPORT quotes the line it prints; a repository not installed on this machine has nothing to reach, and the base always is
Who
whoever merged
Settled by
campaign-installed.py check, which reads whether each install contains everything merged; scripts/campaign-close.py's installed gate refuses a campaign's close while one does not

A merge leaves the install behind on every machine that has it, whether or not that machine holds the campaign, and only a reach catches it up.

Evidence: spec/campaign/directory/system.als § reach, reachDiscipline
It is what refills `current`, and the only thing that does, so a merge on an installed repository is followed by exactly this or the campaign holding it does not close (`reachDiscipline`).
  • spec/campaign/directory/system.als, reach
  • spec/campaign/directory/system.als, reachDiscipline
  • AGENTS.md § Installed repositories

Close: when is the sub-issue settled?

Next step
the merge closes the sub-issue through the pull request's Closes line; a dropped one is closed as not planned; one whose work lives only under <campaign>/scripts/ closes as completed with no pull request; then the claim is released with scripts/campaign-claim.py release, which deletes the ref and, when a worker releases, compacts its pane
Who
GitHub, on the merge; for the release, either role, since no role row restricts it: the worker ends its lifecycle with it, and on the base the planner releases after every merge
Settled by
scripts/campaign-tracker.py settlement <N>, which reads closed with its pull request merged, or closed as not planned; release reads check-merge-review.py again before it deletes a merged claim's ref

Completion is a GitHub fact. Nothing on a terminal screen is evidence that a sub-issue is done, and both ways of closing are needed, or a sub-issue dropped on purpose never reads settled and its campaign can never close.

Evidence: spec/campaign/github/system.als § closeIssue, release
Nothing forbids closing an issue whose pull request never merged.

  • spec/campaign/github/system.als, release
  • scripts/campaign-claim.py, release's compaction note: who releases
  • AGENTS.md § Completion, liveness, and local-only work

Not stated in the source
