시나리오 · 테스트 · 코드를 묶는 witnesses 와 drives

fun tie: Artifact -> Artifact -> Artifact {
  { s: Written & stage.Spec, t: Written & stage.Test, k: stage.Code |
    t->s in witnesses and t->k in drives }
}
pred tied[k: Artifact] { some tie.k }
pred treeTied { all k: Written & stage.Code | tied[k] }

둘 다 테스트에서 읽지만, 읽는 방식이 다르다. witnesses 는 테스트의 텍스트에 적힌 선언이다 — # witnesses: <이름> 줄이고, scripts/check-sdlc-tie.py 가 선언된 명령 이름과 정확히 맞춰 본다. drives 는 두 이름의 짝이다 — 테스트의 파일 이름과 코드 경로의 파일 이름이 서로를 가리키는 동안만 성립한다. 시나리오 쪽 이름을 바꾸어 묶음이 끊기는 것이 S4b_RenameOfTheScenarioBreaksTheTie 이고, 방향을 되돌리면 그 하나가 UNSAT 이 된다. spec/sdlc/system.als:146-163 @ 89918aa

#268 이전에는 하나의 names 였고, 그것이 대상 쪽에서만 끊겼다. 그래서 테스트의 이름을 바꾸면 모형에서는 아무 짝도 떨어지지 않는데 검사기의 T2 는 거절했다 — t->k 는 스위트의 이름에서 읽는데 합쳐진 관계는 그것을 텍스트라고 불렀기 때문이다. 쪼개고 나면 drives 는 어느 쪽 끝을 바꾸어도 떨어지고 (S4c_RenameOfTheTestBreaksTheTie, SAT), witnesses 는 자기 출발점의 이름이 바뀌어도 살아남는다 (S4d_RenameOfTheTestKeepsItsWitness, UNSAT). 두 명령이 그 비대칭을 고정한다. spec/sdlc/system.als:94-121, spec/sdlc/scenarios.als:205-229 @ 89918aa

단계별 건너뛰기 규칙

두 입력이 있고 어느 하나만으로는 건너뜀이 허가되지 않는다. maySkip[c, s] 는 s in c.profile.optional and criterion[c, s] 다. spec/sdlc/system.als:148-173 @ 6eafc16

단계 skippable 기준 — criterion[c, s] 기준이 말하는 것
Intent 아니다 없음 의도가 없는 변경은 그 아래 무엇으로도 판정할 수 없다
Plan 아니다 없음 campaign-claim take 가 ## Plan 없는 하위 이슈의 클레임을 이미 거절한다
Spec 맞다 no writtenOf[c] & stage.(Docs + Test + Code) 그 아래에 아무것도 없다 — 형식화할 것도, 없는 모형을 두고 그릴 것도 없다
Docs 맞다 no writtenOf[c] & GrowsShape 모형이 모양을 키우지 않았다 — 사람에게 보일 것이 없다
Test 맞다 no writtenOf[c] & stage.(Test + Code) 도는 것이 없다
Code 맞다 no writtenOf[c] & stage.(Test + Code) 도는 것이 없다. Test와 Code가 기준을 나누어 갖는 것은 의도적이다 — 코드 경로 없는 테스트는 아무것도 목격하지 않고, 테스트 없는 코드 경로는 검사받지 않는다

GrowsShape 는 spec/ 아래 더해진 sig, var, 또는 one sig ... extends Event 이고, 차이만 보고 읽힌다. 그래서 Docs의 기준은 작업자가 아니라 검사가 정한다. spec/sdlc/system.als:110-115 @ 6eafc16

종류의 프로파일

developmentProfilep.optional = skippable — 이 종류는 기준 아래로 좁히는 것이 없다
prototypingProfilep.optional = Spec + Docs — 도는 것은 절대 가지 않는다. 이 종류만이 maySkip 의 프로파일 쪽 절반을 목격한다
researchProfilep.optional = skippable — 저장소를 스크래치 탐침 너머로 바꾸기를 거절하므로 Plan 아래 모든 단계가 건너뛸 수 있다

프로파일은 종류가 기준 아래로 좁히는 것이고, development와 research는 아무것도 좁히지 않는다. 코드 경로를 쓴 변경은 기준이 이미 Spec과 Test의 건너뜀을 거절하고, 모양을 키운 변경은 기준이 이미 Docs의 건너뜀을 거절한다. 넓힌 것이 더하는 것은 Spec, Test, Code의 건너뜀이고, 각각은 여전히 자기 기준이 문을 지킨다. Test와 Code는 둘 다 쓰지 않은 모든 변경에 가고, 그 시나리오가 무엇을 키웠든 상관없다 (S6b_TheWaiverSurvivesAShape). Spec은 뷰도 쓰지 않은 변경에 간다. Docs는 넓히기 전에도 건너뛸 수 있었고 넓힌 것이 건드리지 않는다. maySkip 은 논리곱이라 프로파일은 기준에 대해 아무 말도 하지 않고, 시나리오가 모양을 키웠으면 Docs의 기준이 그 건너뜀을 거절한다 (S3a_DocsDemanded). 넓힌 것이 남기는 것은 계획 아래에 아무것도 없는 변경보다 넓다. 시나리오와 뷰만 쓴 변경도 착지하고, 그것이 S6a_TheSameWaiverTheKindAllows 다. 그 가운데 가장 좁은 것이 계획 아래에 아무것도 없는 변경 — 절차 참조문, README, 주석 — 이고 S2a_ProseOnlyChange 가 그것을 목격한다, 그리고 그것이 바로 Docs만 대는 프로파일이 기준을 읽기도 전에 곧장 거절하던 변경이다. spec/sdlc/scenarios.als:13-45, spec/sdlc/scenarios.als:109-125, spec/sdlc/scenarios.als:139-146, spec/sdlc/scenarios.als:226-262 @ 6eafc16

prototyping의 Spec 은 좁은 것이 아니라 죽어 있다. 기준이 Spec의 건너뜀을 허락하는 것은 그 변경이 Docs, Test, Code에 아무것도 쓰지 않았을 때뿐인데, 이 종류는 Test도 Code도 보내주지 않으므로 그런 변경은 착지하지 못한다. 착지하는 변경은 코드 경로를 썼고, 그러면 기준이 Spec을 거절한다. S7_PrototypingNeverWaivesItsScenario 가 UNSAT 이고 같은 크기에서 S7a_TheKindThatDoes 가 SAT 이므로, 거절하는 것은 모양도 크기도 아니다. 프로파일이 살려두는 것은 Docs의 건너뜀뿐이다. spec/sdlc/scenarios.als:264-278 @ 6eafc16

여기에 종류의 원자는 없다. 모형은 프로파일과 변경이 어떻게 합쳐지는지를 갖고, 종류가 자기 프로파일을 갖는다. 그래서 종류를 더해도 모형은 바뀌지 않는다. 나머지 종류의 프로파일 줄은 .claude/skills/opening-campaign/assets/agents/ 밑 파일이 이 어휘로 쓴다. spec/sdlc/system.als:73-84, spec/sdlc/scenarios.als:13-45 @ 6eafc16

건너뛰기 규칙을 읽는 두 자리

읽는 자리모형의 식별자무엇인가
작업자가 단계에 닿아서 읽는다 skipDiscipline — Now.event = Skip implies maySkip[Now.subject, Now.at] 정하는 읽기가 아닌 이른 읽기
변경이 착지할 때 다시 읽는다 landDiscipline — Now.event = Land implies all s: absentStages[Now.subject] | maySkip[Now.subject, s] 착지는 병합이므로 병합을 막는 자리, 곧 풀 리퀘스트의 check
착지한 변경의 빠진 단계는 모두 허가받은 것이다 AbsenceLicensed / AbsenceLicensed_Bites 검사와, 그 규율 없을 때의 반례

spec/sdlc/scenarios.als:58-63, spec/sdlc/scenarios.als:73-81, spec/sdlc/checks.als:42-52 @ 6eafc16

구제책은 뷰를 결국 쓰는 것이다. 건너뛴 단계를 쓰면 그 건너뜀이 철회된다 — 단계는 쓰이거나 건너뛰어지지, 둘 다는 아니고, 쓴 쪽이 나중 말이다. S3b_DocsWrittenAfterAll 이 그 사슬이고, 철회를 읽는 하나뿐인 명령이다. spec/sdlc/system.als:195-199, spec/sdlc/scenarios.als:148-162 @ 6eafc16

land[c] 는 구조적으로 모든 단계가 끝났음 — 쓰였거나 건너뛰어졌음 — 을 기다린다. 그것은 정의이지 기계가 아니다. 그 빠짐이 허가되었는지 는 landDiscipline 의 것이고, 쓰인 것이 묶이는지 는 tieDiscipline 의 것이다. spec/sdlc/system.als:233-247 @ 6eafc16

모형 밖에 남긴 것

  • 세 기계는 규율이지 사실이 아니다 — orderDiscipline, tieDiscipline, landDiscipline 은 각각 검사 하나가 가정하고 그 _Bites 가 떨어뜨린다. 이벤트에 써 넣은 규칙은 모형이 인정하는 모든 세계에서 참이고, 어떤 명령도 그것의 부재를 보일 수 없기 때문이다. 그래서 이벤트는 느슨하다: write 는 순서를 읽지 않고, skip 은 기준을 읽지 않고, land 는 묶음을 읽지 않는다. spec/sdlc/system.als:38-44 @ 6eafc16
  • 아무것도 open 하지 않는다 — 검사가 도는 순간은 커밋이고, campaign/github 는 커밋을 모형화하지 않는다. 묶음은 트리 하나 안 파일들 사이의 것이고, spec/campaign 의 어떤 개체도 그것을 들고 있지 않다. Change 를 Issue 와, Land 를 MergePullRequest 와 합치는 것은 이 층 위의 층이다. spec/sdlc/system.als:6-11 @ 6eafc16
  • 누가 파일을 처음 썼는지 말하지 않는다 — 변경이 다시 쓰는 산출물, 이미 있던 시나리오를 목격하는 테스트 같은 것도 여기서는 그 변경이 쓴 것만큼이나 그 변경의 산출물이다. 검사는 이름을 차이가 아니라 트리에 대고 읽는다. spec/sdlc/system.als:93-97 @ 6eafc16
  • 검사가 트리를 읽는지 차이만 읽는지는 검사의 것이다 — 모형은 묶음이 무엇인지와 언제 하나가 읽히는지를 말한다. spec/sdlc/system.als:138-139 @ 6eafc16
  • 이름 바꾸기 뒤 무엇이 살아남는지는 솔버에게 맡긴다 — witnesses' 는 a의 들어오는 짝 가운데 아무것이나 남기고 나머지를 떨어뜨리고, drives' 는 양쪽 끝의 짝에 대해 같은 자유를 갖는다. 같은 커밋이 다시 쓴 텍스트를 모형이 따로 세지 않기 때문이다. spec/sdlc/system.als:253-261 @ 89918aa
  • 도달 가능성 바닥이 따로 있다 — 어떤 흔적도 닿지 못하는 이벤트는 명령들에서 질문 하나를 조용히 없애고, 너무 조인 프레임이 어떤 명령도 빨갛게 하지 않으면서 그것을 일으키는 가장 싼 길이다. 그래서 Cov_Write, Cov_Skip, Cov_Rename, Cov_Land 가 있다. spec/sdlc/checks.als:66-74 @ 6eafc16
