The three planes

Every artifact of a campaign sits on one of three planes, the base, a member repository or the campaign, and each is stored on a remote, so it survives the machine; the campaign directory is no plane, only one machine's cache of the three.

What does the base hold?

Holds
AGENTS.md, CLAUDE.md, README.md, .gitignore, .claude/, spec/, scripts/, .github/, docs/: how campaigns are run.
Stored in
this repository, kalaluthien/campaign-base
Survives the machine
yes

.gitignore is an allowlist: it ignores everything at the root and admits only the base's own entries, so a campaign directory and every clone inside it stay untracked and cannot be committed here by accident. scripts/check-tree-shape.py refuses a commit that tracks a top-level entry the allowlist does not name.

What does a member repository hold?

Holds
the code being changed and its history; from a campaign, only a claim branch and its pull request
Stored in
each repository's own remote
Survives the machine
yes, once pushed; the clone under repos/ does not

Every sub-issue is filed on the base's tracker, whichever repository its code lands in, so a member repository's own issue conventions are never touched. Its ## Lands in section says where the work goes, because where the issue is filed no longer does.

Evidence: spec/campaign/github/system.als § Issue
Every issue is FILED on the Base's tracker, whatever its `repo`; a member repository receives only branches and pull requests, so the tracker is a constant here and not a field.

What does the campaign hold?

Holds
the campaign issue, whose body is the charter (## Intent, ## Scope, ## Definition of done, ## Repos); its labels, campaign, campaign:<slug> and bound:<machine>; its sub-issues, linked as sub-issues, which is the whole index; every comment, each opening with its kind; and each claim, a <slug>/<issue>-<topic> ref on the remote
Stored in
GitHub issues on kalaluthien/campaign-base, and the claim refs on the remotes
Survives the machine
yes: any machine, or a phone, reads it without anything local agreeing

A campaign is its campaign issue. Progress is not written anywhere: scripts/campaign-tracker.py settlement derives it from the sub-issue index, so the body changes only when the scope does and at the close.

Evidence: spec/campaign/github/system.als § Campaign, Claimed
the sub-issues whose branch is on the remote. A branch is a ref, readable from any machine, so the claim is a GitHub fact and not a local one -- which is why it lives here.
  • spec/campaign/github/system.als, header, Campaign and Claimed
  • AGENTS.md § The campaign issue body
  • AGENTS.md § ID, slug, directory, branch

What does the campaign directory hold, and why is nothing durable only there?

Holds
.campaign, the marker naming the campaign; AGENTS.md and CLAUDE.md, the campaign's principles; README.md, derived from the campaign issue body; runtime/, derived state and process artifacts such as a pid, a log, a lock; scripts/, scratch; repos/, the member clones
Stored in
campaign-<slug>-<date>/ at the base root, git-ignored, on one machine
Survives the machine
no, and it need not: at the close scripts/campaign-close.py deletes it on the person's --delete, and nothing is lost

A sub-issue's plan, a session's state at a stop and the campaign's progress go on the issue they are about, as a comment, where every session and every machine reads them. What stays in the directory is what no issue can hold, or what can be derived again from one at any time. That is what lets the directory be optional off the bound machine.

Evidence: spec/campaign/directory/system.als, header
A campaign directory holds no fact another machine reads, which is what lets it be optional.
  • spec/campaign/directory/system.als, header
  • AGENTS.md § The three planes
  • scripts/campaign-directory.py: which directory on this machine is a campaign's, read from its marker
  • scripts/campaign-close.py, here: the delete is the person's word

How does a merge reach a repository installed on this machine?

Two checkouts
the install, where the repository is used, and the clone under the campaign directory, where it is worked
The base's row
installed at the base root; its apply is scripts/install-hooks.sh
Any other
a ## Repos entry carrying (installed: <path>, apply: <command>)

A merge is not finished until the install shows it. Whoever merges runs scripts/campaign-installed.py reach for the repository the merge landed in; check reads whether an install is behind, and the campaign's close refuses while one is.

Evidence: spec/campaign/directory/system.als § Machine, reach
An installed repository has two checkouts on a machine -- the install, where it is used, and the clone under the campaign directory, where it is worked -- and a merge is not finished until the install shows it.
